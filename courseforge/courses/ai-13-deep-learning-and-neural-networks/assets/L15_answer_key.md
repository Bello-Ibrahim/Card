## Notes for the course team

- **Notebook D content issue (RESOLVED 2026-09-23: L15 and the M3 quiz now say the leak comes from a logged loss whose graph was never used for backward()).** The lesson says storing the loss tensor "keeps each step's computation graph in memory". This is only true for a graph that has *not* been through `backward()`. When `loss.backward()` is called on the stored tensor itself (the usual training step), PyTorch frees the saved activations, and in our CPU test memory did not grow measurably (about 720 MB to 743 MB over 60 steps, the same as with `.item()`). To make the symptom real, the notebook fills in the lesson's `...` with a training step followed by a log line that recomputes the batch loss after the update (`loss = loss_fn(model(xb), yb)`). That logged tensor's graph is never freed, so memory grows by several MB per step. The lesson lines `losses = []`, `for xb, yb in train_dl:` and `losses.append(loss)  # keeps every graph alive` are kept exactly. The `.item()` fix (or computing the logged loss under `torch.no_grad()`) solves it. Consider adding to the lesson that the leak happens when the stored loss's graph was not used for `backward()`, for example a logged or validation loss.
- **Notebook D on GPU.** On a Colab GPU runtime the notebook prints `torch.cuda.memory_allocated()` and shows the same steady rise; one epoch (50 steps) will not fill a 15 GB GPU, so learners see growth, not an actual OOM error. Not tested on GPU (no GPU was available).
- **Notebook A.** The training loop uses `model(X).squeeze(1)` so that the MSE loss compares shapes `(512,)` and `(512,)`; without it, `MSELoss` would broadcast `(512, 1)` against `(512,)` and add a second, unrelated bug.
- **Notebook C** uses synthetic 10-class data (2,048 examples, 64 features) and SGD with lr 0.05, so it runs in a few seconds on CPU.
- All data is synthetic; no download is needed. Notebook D uses Fashion-MNIST-shaped random data (784 features, 10 classes).
